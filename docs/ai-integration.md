2026-11-12, `feat/seungyoon-ai` 작업 브랜치 기준. develop 및 main에 병합하지 않는다.

전체 이슈를 완료한 상태로 표시하지 않는다. 현재 코드에는 농장, 텃밭의 실제 조회 구현이 없어 기본 조회는 빈 결과다. 존재하지 않는 농장이나 담당자를 만들어 연결하지 않는다.

## 팀 도메인 접점

1. `CaretakerFarmReader`는 등록 가능한 실제 농장의 ID와 이름을 제공해야 한다. 기본 구현은 빈 결과이며 관리사 등록은 C404다.
2. `CareGardenReader`는 목록과 개별 조회에서 같은 텃밭 ID, 관리사 로그인 아이디, 주인 로그인 아이디를 제공해야 한다. `findGardenForUpdate`는 호출 트랜잭션 동안 실제 텃밭 행을 잠가야 한다. 프로필의 관리사 ID와 로그인 아이디를 혼동하지 않는다.
3. 작업 입력 `guidance`는 검증된 자료의 출처, 단계, 최소 반복 간격, 문구, 작업 시간이다. LLM이 농법이나 시간을 만들지 않는다. 자료가 없으면 5분 관찰 작업만 제공한다.
4. 성장 계산 입력은 실제 시작일, 기준 온도, SEED 0부터 엄격히 증가하는 SPROUT, FLOWER, FRUIT 적산온도 기준이다. 예시 숫자를 운영에 기본값으로 넣지 않는다.
5. `VoiceTaskReader`는 `TaskVoiceReader`로 구현했다. 실제 텃밭 조회가 연결되면 동일 작업의 업로드, 확정, 완료 흐름을 사용할 수 있다.
6. 주인 프로필로 텃밭을 연결할 때 첫 작업 생성은 `TaskGenerationService.generate(담당자, 오늘)`를 연결 트랜잭션 커밋 후 호출할 수 있다. 첫 일기는 팀 일기 서비스에서 만든다. 아직 자동 연결되어 있지 않다.
7. `CareLog`에는 원문과 요약을 분리 저장한다. 가족 일기 모듈은 이 기록과 `GrowthEvent`를 읽어야 한다. 하트 수 역시 실제 하트 처리에서 `CareLog.heartsReceived`에 반영해야 한다. 현재 증감 API는 추가하지 않았다.
8. 수확 API는 소유권 확인 후 `GrowthStatusService`에서 저장한 예측일을 읽는다. 성장 계산 기록이 없으면 기존 `HarvestGardenReader` 예측일을 유지한다. 기록은 있지만 예측일이 null이면 과거 날짜를 대신 노출하지 않는다. 실제 농장과 위치, 담당자 등은 여전히 `HarvestGardenReader` 구현이 필요하다. 수확 가능 여부는 기존 텃밭 데이터 기준이며 예측 단계만으로 수확 가능하다고 바꾸지 않는다.

## 작업과 성장 동작

1. `/caretaker/tasks/today`는 당일 기록이 없는 텃밭의 작업을 생성한 뒤 묶어서 반환한다. 실제 담당 텃밭이 없으면 목록이 빈다. 담당자 전체 작업 시간은 최대 120분이다. 시간이 모두 배정되면 뒤 텃밭의 작업이 비어 있을 수 있다.
2. AI 호출은 저장 트랜잭션 밖에서 수행한다. 저장 시 담당자와 날짜별 `TaskDay`를 잠그고 예산과 현재 날씨, 단계를 다시 검사한다. 기존 작업은 삭제하거나 다시 생성하지 않는다. 예보나 단계가 바뀌어 미완료 작업이 전부 숨겨진 경우에만 남은 예산 안에서 관찰 작업을 한 번 추가한다. 같은 요청에 텃밭이 중복되어도 관찰 작업은 하나다. 숨겨진 작업의 시간도 예약 예산에 포함하므로 예산이 꽉 차면 관찰 작업을 추가하지 않는다. 모두 완료한 텃밭에는 새 관찰 작업을 만들지 않는다.
3. 비 예보 또는 오래된 날씨 정보에서는 물 주기를 제외한다. 조회와 완료 시에도 다시 검사하므로 오래된 카드로 제외된 작업을 완료할 수 없다. 제외된 작업은 남은 작업 수에 포함하지 않는다.
   반복 방지 이력은 최소 14일과 안내 자료의 가장 긴 반복 간격 중 긴 기간을 사용한다. 작업 예정일이 아니라 실제 완료 시각으로 조회하므로 늦게 완료한 작업도 간격 검사에 반영한다. 이상 징후 조회의 최근 7일 범위는 별도로 유지한다. MariaDB 지원 범위를 벗어나는 과거 날짜는 조회하지 않는다.
4. 작업 완료는 작업 행을 잠그고 담당자와 사진 및 확정 메모의 소속을 검사한다. 돌봄 기록, 완료 상태, `NotificationService.send` 알림 저장은 한 트랜잭션이다.
5. 사진 확인은 선택한 로컬 비전 모델만 사용한다. 비전 실패 시에도 사진을 저장하고 `aiCheck=null`로 반환한다. 자동으로 작업을 완료하거나 실제 작업을 증명하지 않는다.
6. 성장 계산은 완료된 날짜의 일평균 기온을 사용한다. 자료가 누락되면 C502이며 이전 상태를 덮어쓰지 않는다. FLOWER 또는 FRUIT 확인 시 그날의 기준으로 보정하고 이후 완료된 날의 기온만 더한다. NO_CHANGE는 보정하지 않는다.
7. 같은 상태를 다시 계산하면 단계 이벤트를 중복 생성하지 않는다. 단계 상승 시 성장 이벤트와 알림을 저장한다. 최근 7일 적산온도가 유지된다는 가정으로 수확일을 예측하며 자료 부족 또는 저온에서는 null이다. 생물학적 수확 판정을 대신하지 않는다.
   관리사 카드와 완료 응답의 `stageCheck`는 저장된 단계와 실제 확인 단계를 비교한다. FLOWER를 확인하면 같은 단계에서 다시 묻지 않고, FRUIT로 올라가면 확인을 요청한다. NO_CHANGE는 보정하지 않으므로 확인 요청이 유지된다.
8. 스케줄은 Asia/Seoul 기준 성장 04:00, 작업 생성 05:00이다. 내부 API는 기존 `X-Service-Key` 검증을 사용하며 당일 계산만 지원한다. 성장 배치는 `updated`, `failed` 수를 반환한다.

## 비용 없는 모델 연결

1. 기본값에서는 모델을 실행하지 않는다. 작업은 규칙 대체를 사용하고 음성은 재시도 가능한 실패 상태, TTS는 C502를 반환한다. 모델 기능이 동작한 것처럼 가짜 결과를 만들지 않는다.
2. 이미 내려받은 로컬 Ollama 모델이 있으면 `AI_LOCAL_ENABLED=true`, `AI_LOCAL_MODEL`을 설정한다. 비전은 별도 `AI_LOCAL_VISION_MODEL`이 있어야 한다. 주소는 loopback HTTP만 허용한다.
3. 로컬 STT는 [설치 안내](../local-ai/README.md)에 따라 faster-whisper와 로컬 모델 파일을 준비한 뒤 `AI_LOCAL_STT_ENABLED=true`로 켠다. 자동 모델 다운로드와 유료 제공자로의 전환은 없다. 이번 환경에는 모델이 설치되지 않아 실제 추론은 검증하지 못했다. 프로젝트 안에 가상 환경과 pip를 준비했지만 패키지 설치에서 배포본을 받지 못했고 PyPI 직접 조회도 시간 초과로 실패했다. 모델 설치 성공 또는 Python 버전 호환성을 확인한 것으로 해석하지 않는다.
4. 로컬 추론 서버는 백엔드와 같은 호스트에 있어야 한다. Vercel 프론트와 배포된 백엔드가 노트북의 localhost에 접속하는 구조는 아니다.
5. TTS는 최대 300자, 속도 0.5부터 1.5, 동일 문장과 속도별 최대 32개 캐시다. 실제 음성 생성 구현은 없으므로 프론트의 브라우저 읽어주기 대체를 사용한다. 수당은 `CARE_ALLOWANCE_PER_TASK`, 기본 0이며 가정치로 표시한다.

## 배포와 검증

1. `src/main/resources/db/manual/voice_memo.sql`, `care_growth.sql`은 새 테이블용 수동 SQL이다. 기존 스키마와 충돌 여부를 확인하고 스테이징에 적용한 뒤 prod의 `ddl-auto=validate`로 검사한다. 이번 작업에서는 DB에 적용하지 않았다.
2. 테스트는 `./gradlew test --tests 'community.likelion.growwithusserver.ai.*' --tests 'community.likelion.growwithusserver.voice.*' --tests 'community.likelion.growwithusserver.care.*' --tests 'community.likelion.growwithusserver.growth.*' --tests 'community.likelion.growwithusserver.caretaker.*'`로 실행할 수 있다. Python 검사는 `python -m unittest discover -s local-ai -p 'test_*.py'`다.
3. 현재 환경은 Gradle 9.8.2 다운로드와 일부 의존성 접근이 차단되어 전체 Gradle 빌드를 실행하지 못했다. 프로젝트 버전은 바꾸지 않았다. JDK 25의 `--release 21`과 캐시된 의존성으로 핵심 서비스 및 저장소 인터페이스를 컴파일하고 JUnit 검사를 실행했다. HTTP 컨트롤러, 보안 필터, 실제 DB 통합 검사를 대신하지 않는다.
4. MariaDB 행 잠금, 동시 완료와 확정, 알림 롤백, 실제 파일 녹음, 모델 지연, 프론트 연동, 서버 부팅은 통합 환경에서 확인해야 한다. 단위 검사 통과를 서비스 전체 완료로 해석하지 않는다.
5. 캐시된 의존성으로 핵심 서비스 JUnit 43개가 통과했다. 기존 검사에 긴 작업 반복 간격, 실제 저장 파일의 재시도용 읽기, 외부 주소와 경로 이탈 및 용량 초과 거절 검사를 추가했다. DB와 실제 모델 대신 저장소 및 모델 대역을 사용하며 파일 검사는 임시 디렉터리의 실제 파일로 수행한다. 완료 시각 기준 JPQL과 MariaDB 실행 계획 검사는 실제 DB에서 별도로 해야 한다. Python 21개 검사는 직전 변경에서 통과했으며 이번 변경은 Python 코드를 수정하지 않았다.
6. `care_task`에 완료 이력 조회용 `idx_task_garden_completed(garden_id, completed_at)` 인덱스를 추가했다. 새 테이블용 수동 SQL에 포함되며, 이미 만들어진 테이블은 같은 인덱스가 있는지 확인한 뒤 별도로 추가해야 한다. 이번 작업에서 운영 DB 변경은 실행하지 않았다.
