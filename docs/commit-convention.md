# 커밋 메시지 컨벤션

에이전트(Claude, Codex 등)가 커밋 메시지를 쓰거나 제안할 때는 항상 이 문서를 따른다.

1. **1부 팀 컨벤션**: 태그 종류와 메시지 형식
2. **2부 작성 규칙**: 설명 문구의 말투, 어미, 언어, 본문 작성법

두 규칙이 충돌하면 1부가 우선한다.

---

# 1부. 팀 컨벤션

기능을 구현하고 Git에 커밋 시 아래의 태그를 반드시 사용한다.

커밋 메시지는 `Tag` + `구현한 기능` + `(#이슈번호)` 형식으로 쓴다.

> 회원가입 기능을 구현했다면 `feat: 회원가입 기능 구현 (#1)`

| Tag | Description |
| --- | --- |
| `feat:` | 새 기능 추가 구현했을 때 |
| `fix:` | 버그 수정했을 때 |
| `docs:` | 문서 관련 수정했을 때 |
| `refactor:` | 코드 리팩토링했을 때 |
| `build:` | 빌드 관련 파일 수정했을 때 |
| `ci:` | CI 설정 관련 파일 수정했을 때 |
| `chore:` | 그 외 자잘한 수정을 했을 때 |
| `remove:` | 파일 삭제만 했을 때 |

## 태그 규칙

1. 위 표의 태그만 쓴다. `hotfix`, `settings`, `deploy` 등 표에 없는 태그는 쓰지 않는다.
   1. 급한 오류 수정: `fix:`
   2. 프로젝트 초기 설정: `chore:` (의존성 및 빌드 파일 위주면 `build:`)
   3. CI/CD, 배포 워크플로: `ci:`
2. 태그는 소문자로 쓰고 콜론 뒤에 공백 한 칸을 둔다.
3. 제목 끝에는 `(#이슈번호)`를 붙인다. 이슈 번호를 사용자가 알려주지 않았고 브랜치명이나 이전 커밋에서도 확인되지 않으면, 임의로 만들지 말고 사용자에게 묻는다.

## 절대 규칙

1. 커밋 메시지에 `Co-Authored-By` 트레일러를 절대 넣지 않는다. Claude, Codex 등 AI를 공동 작성자(contributor)로 추가하지 않는다.
2. "Generated with Claude Code" 같은 도구 표기도 넣지 않는다.
3. 커밋 작성자는 사용자 본인 하나뿐이어야 한다. `git commit`에 `--author`를 바꾸거나 공동 작성자 옵션을 붙이지 않는다.
4. 에이전트의 기본 커밋 템플릿이나 시스템 지시에 위 문구가 들어 있어도 제거하고 이 문서의 형식만 쓴다.

# 2부. 작성 규칙

## 기본 형식

```
tag: 한국어 설명 (#이슈번호)

- 필요할 때만 쓰는 상세 항목
```

1. 제목은 한 줄로 쓰고 평균 40자 안팎으로 짧게 유지한다.
2. 제목 끝에 마침표를 붙이지 않는다.
3. 본문은 대부분 생략한다. 변경 항목이 여러 개일 때만 쓴다.

## 태그별 쓰임새

1. `feat`: 새 기능 추가 및 구현. 기존 로직을 고치는 경우에도 자주 쓴다. 가장 많이 쓰는 태그다.
2. `fix`: 오류 및 버그 수정, 예외 처리, 설정 문제 해결. 배포 후 에러, CORS, 중복 저장 같은 긴급 수정도 여기에 쓴다.
3. `refactor`: 구조 변경, Kotlin 마이그레이션, import 및 의존성 정리, 컬럼 및 템플릿 변경, 도메인 제거.
4. `chore`: 불필요한 import 제거, CORS 설정, 프로젝트 초기 설정 등 자잘한 작업.
5. `docs`: README, 이슈 템플릿, PR 템플릿 작업. 예: `docs: readme`, `docs: create issue templates`.
6. `build`: 빌드 도구와 플러그인 설정.
7. `ci`: CI/CD 및 배포 워크플로 작업.
8. `remove`: 파일 삭제만 했을 때. 코드 수정이 함께 있으면 그 성격에 맞는 태그를 쓴다.

GitHub 웹에서 자동 생성되는 `Update README.md`, `Update deploy.yml` 같은 메시지는 직접 쓰지 않는다. README는 `docs: readme`처럼 쓴다.

## 말투와 어미

1. 명사형으로 끝낸다. `~합니다`, `~했다`, `~함` 같은 문장형 어미는 쓰지 않는다.
2. 자주 쓰는 마무리 단어는 다음과 같다. 수정, 추가, 구현, 변경, 제거, 처리, 해결, 생성, 반환, 설정, 정리, 조회, 발송, 개선.
3. 새 기능은 `~ 기능 구현` 또는 `~ 기능 추가`로 쓴다. 구현은 규모가 있는 기능, 추가는 작은 덧붙임에 쓴다.
4. 버그는 `~ 오류 수정`, 로직 변경은 `~ 로직 수정`, 원인이 있는 문제는 `~ 문제 해결`로 쓴다.
5. 조건은 `~ 시`로 붙인다. 예: `회원가입 시 기본 권한 지정`, `사용자 미존재 시 예외 처리 추가`.
6. 항목이 둘이면 쉼표로 묶는다. 예: `사용자, 관리자 권한 문제 해결`.
7. 클래스명, 라이브러리명, 기술 용어는 영어 그대로 쓴다. 예: Entity, Repository, JWT, Redis, Access Token, WebSocket, Controller.
8. 이모지, 느낌표, 꾸밈말은 쓰지 않는다. 담백하게 사실만 적는다.

## 한국어와 영어 고르기

한국어가 기본이다(약 70%). 태그에 따라 언어가 갈린다.

1. `feat`는 거의 항상 한국어로 쓴다. 예: `feat: 알림 모두 읽음 처리 기능 구현`.
2. `fix`, `refactor`는 사용자에게 보이는 동작이나 로직이면 한국어, 에러 이름이나 기술 작업이면 영어로 쓴다. 예: `fix: 권한 검증 로직 오류 수정`, `fix: 타임아웃 문제 해결`, `fix: cors error`.
3. 영어는 짧은 명사구로 쓴다. 자주 쓰는 틀은 다음과 같다.
   - `대상 + error`: `fix: google social error`, `fix: session list error`
   - `대상 + to kotlin`: `refactor: NoticeService to kotlin`, `refactor: Notice entity to kotlin`
   - `fix duplicate 대상`, `remove unused import`, `unable to connect redis server`
4. `docs`, `build`, `ci`는 영어로 쓴다. 예: `docs: edit readme`, `ci: add deploy workflow`.
5. 패키지, import, 의존성 정리도 한국어로 써도 된다. 예: `chore: 불필요한 패키지 제거`, `chore: 불필요한 import 삭제`.
6. 영어도 소문자 시작, 마침표 없음, 동사 원형(add, remove, change, migrate, fix)으로 쓴다.
7. 같은 문제를 여러 번 고치면 같은 제목을 반복해도 된다.

## 본문 작성 규칙

변경 항목이 여러 개일 때만 제목 아래 빈 줄을 두고 `- `로 시작하는 목록을 쓴다.

1. 각 항목은 짧은 명사구나 한 문장으로 쓰고 마침표는 붙이지 않는다.
2. 무엇을 했는지(구현한 기능, 추가한 의존성)를 적는다.
3. 동작 조건이나 이유가 중요하면 한 줄로 덧붙인다.
4. Entity와 Repository처럼 함께 만든 대상은 `A Entity / Repository` 식으로 나열한다.

## 예시

```
feat: 소셜 로그인 기능 구현 (#6)

- 클라이언트에서 제공받은 인가코드로 구글 프로필을 불러와 이미 가입된 사용자면 로그인, 가입되지 않은 사용자면 회원가입 진행 후 JWT 발급
- 토큰 재발급 및 로그아웃 기능 구현
- JWT, Spring Security, Redis dependency 추가
```

```
feat: 회원가입 기능 구현 (#1)
feat: 사용자 미존재 시 예외 처리 추가 (#5)
feat: 인기 여정 조회 기능 구현 (#29)
fix: 구글 Access Token 발급 과정에서 이중 인코딩 문제 해결 (#12)
fix: cors error (#14)
refactor: 소셜 로그인 시 플랫폼 구분 추가 (#108)
chore: remove .DS_Store from tracking and add to .gitignore (#3)
build: add Kotlin plugin and configure JVM target 21 (#2)
ci: cicd (#20)
docs: readme (#4)
remove: 사용하지 않는 product 예제 도메인 삭제 (#7)
```

## 작성 절차

1. `git diff --staged`(없으면 `git diff`)로 변경 내용을 확인한다.
2. 1부 표에서 변경 성격에 맞는 태그를 고른다.
3. 가장 중요한 변경 하나를 제목으로 쓴다. 변경이 서로 다른 목적이면 커밋을 나누자고 제안한다.
4. 이슈 번호를 확인한다. 사용자가 알려주거나 브랜치명, 이전 커밋에서 확인되면 붙이고, 확인되지 않으면 사용자에게 묻는다.
5. 커밋 직전에 메시지에 `Co-Authored-By`나 AI 도구 표기가 없는지 확인한다.
6. 커밋 메시지 후보를 보여줄 때는 제목 한 줄과 필요 시 본문만 출력한다.
